## 클래스와 인스턴스

> **풀고 싶은 문제**
> ticle_lite 라이브러리로 초음파 센서를 사용할 때, sr04 = SR04(trig=2, echo=3)로 인스턴스를 만들고 sr04.read()로 장애물과의 거리를 읽는 메소드를 호출한다. 이 구조가 어떻게 동작하는지 이해하지 못하면 라이브러리 문서를 보면서도 무엇을 써야 할지 막막하다.

클래스(class)는 비슷한 속성과 동작을 묶어 새로운 타입을 정의하는 틀이다. 인스턴스(object)는 그 틀로 만든 실체다. 버튼 하나를 클래스로, 버튼 세 개를 각각 다른 핀에 연결한 세 인스턴스로 이해하면 된다.

### 클래스 정의와 인스턴스 생성

```python
class Led:
    def __init__(self, pin, active_high=True):
        self.pin = pin                      # 인스턴스 속성
        self.active_high = active_high
        self._state = False

    def on(self):
        self._state = True
        level = 1 if self.active_high else 0
        print(f"핀 {self.pin}: 출력 {level}")

    def off(self):
        self._state = False
        level = 0 if self.active_high else 1
        print(f"핀 {self.pin}: 출력 {level}")

    def toggle(self):
        if self._state:
            self.off()
        else:
            self.on()


# 클래스로부터 두 개의 독립 인스턴스(인스턴스) 생성
red = Led(pin=15)
green = Led(pin=16)
red.on()
green.off()
red.toggle()
print(f"red 핀 번호: {red.pin}")
```

**코드 해설**

__init__은 인스턴스를 만들 때 자동으로 호출되는 초기화 메서드다. self는 지금 만들어지는 인스턴스 자신을 가리키는 매개변수로, 모든 메서드의 첫 번째 인자로 자동 전달된다. self.pin처럼 self.속성명 형태로 쓴 변수는 인스턴스마다 독립적으로 관리된다. red.pin과 green.pin은 서로 다른 메모리 공간에 저장된다.

**실행 결과와 확인할 점**

Led(15)로 인스턴스를 만들면 자동으로 __init__이 실행되어 pin이 15로 설정된다. red와 green은 각각 독립된 상태를 가지므로, red.toggle()이 green의 상태에 영향을 주지 않는다.

> **알아두기 — 밑줄로 시작하는 속성**
> self._state처럼 이름 앞에 밑줄을 붙이면 "외부에서 직접 건드리지 마세요"라는 약속 표시다. 파이썬은 강제하지 않지만, 클래스 내부에서만 쓰는 변수는 이 관례를 따른다.

> **한 걸음 더**
> Led 클래스에 blink(count) 메서드를 추가해 본다. on과 off를 count번 반복하는 구현을 써 보자.

### 상속

라이브러리 클래스를 그대로 쓰다가 동작을 바꾸거나 기능을 추가해야 할 때 상속을 쓴다.

```python
class LedWithLog(Led):
    def __init__(self, pin, active_high=True):
        super().__init__(pin, active_high)  # 부모 __init__ 호출
        self._log = []

    def on(self):
        self._log.append("on")
        super().on()                        # 부모 on() 실행

    def off(self):
        self._log.append("off")
        super().off()

    def history(self):
        return self._log


led = LedWithLog(pin=15)
led.on()
led.off()
led.on()
print(f"동작 기록: {led.history()}")
```

**코드 해설**

super().__init__()은 부모 클래스의 초기화 코드를 그대로 실행한다. 부모의 동작에 앞뒤로 추가 코드를 넣는 이 패턴은 8장 GUI 예제에서 Qt 창 클래스를 상속할 때 그대로 등장한다.

**실행 결과와 확인할 점**

['on', 'off', 'on']이 출력되어야 한다. LedWithLog는 Led의 기능을 모두 이어받으면서 로그 기능만 추가했다.

## 예외 처리

> **풀고 싶은 문제**
> 센서나 액추에이터를 초기화하다가 오류가 나면 I2C 버스나 PWM 채널을 닫지 못한 채 프로그램이 멈춘다. 하드웨어를 안전하게 정리하는 코드가 항상 실행되도록 만들 수 있을까?

코드를 실행하는 도중 예기치 못한 상황이 생기면 파이썬은 예외(exception)를 발생시킨다. try/except로 예외를 잡아 처리하면 프로그램이 멈추지 않고 계속 실행할 수 있다. 하드웨어 코드에서는 정상 종료든 오류 종료든 항상 실행해야 하는 정리 코드를 finally에 넣는다.

### try / except

```python
def safe_divide(a, b):
    try:
        result = a / b
        return result
    except ZeroDivisionError:
        print("오류: 0으로 나눌 수 없습니다.")
        return None


print(safe_divide(10, 2))   # 5.0
print(safe_divide(10, 0))   # 오류 메시지 출력 후 None 반환
```

**코드 해설**

try 블록 안에서 예외가 발생하면 실행이 즉시 except 블록으로 넘어간다. ZeroDivisionError처럼 예외 종류를 명시하면 그 예외만 잡는다. 모든 예외를 잡으려면 except Exception as e:를 쓴다.

### try / except / finally

하드웨어 코드에서는 finally가 핵심이다. 예외가 발생하든 정상 완료하든 finally 안의 코드는 반드시 실행된다.

```python
def measure_with_cleanup(sensor):
    try:
        val = sensor.read()         # 여기서 오류가 나도
        return val
    except OSError as e:
        print(f"센서 오류: {e}")
        return None
    finally:
        sensor.deinit()             # 반드시 실행됨
```

**코드 해설**

sensor.read()에서 OSError가 발생하면 except 블록을 실행한 뒤 finally를 실행하고 함수가 끝난다. 정상적으로 return val이 실행되어도 반환 전에 finally가 먼저 실행된다. 이 구조는 3장부터 이어지는 모든 하드웨어 예제에서 반복해서 등장한다.

> **이 예제로 풀 문제**
> 여러 장치를 초기화하다 중간에 실패하면 이미 초기화된 장치를 닫아야 한다.

```python
def run():
    sensor = None
    lcd = None
    
    try:
        sensor = SR04(trig=2, echo=3)
        i2c = I2CController(sda=10, scl=11)
        lcd = CharLCD(i2c)

        while True:
            dist = sensor.read()
            lcd.text(f"{dist:.1f} cm", 0, 0)
            time.sleep_ms(200)
    except KeyboardInterrupt:
        pass                    # Ctrl+C는 정상 종료로 처리
    finally:
        if sensor:
            sensor.deinit()     # 초기화 완료된 것만 정리
        if lcd:
            lcd.deinit()
```

**코드 해설**

sensor와 lcd를 None으로 미리 선언해 두면 초기화 전에 예외가 발생해도 finally에서 if sensor: 조건이 False가 되어 deinit 호출을 건너뛴다. KeyboardInterrupt는 Ctrl+C로 프로그램을 멈출 때 발생한다. pass로 잡아 두면 오류 메시지 없이 finally 정리 코드만 실행된다.

**실행 결과와 확인할 점**

Ctrl+C를 눌렀을 때 트레이스백 없이 정리 코드가 실행되고 프로그램이 깔끔하게 종료되어야 한다. finally 블록을 삭제하고 Ctrl+C를 눌러 deinit이 호출되지 않는 것을 비교해 본다.

> **한 걸음 더**
> except 블록 없이 try: ... finally: ... 구조도 유효하다. 예외 처리 없이 정리 코드만 보장하고 싶을 때 이 형태를 쓴다. 직접 시험해 본다.

## with 문과 컨텍스트 매니저

> **풀고 싶은 문제**
> 센서나 액추에이터 인스턴스를 사용할 때마다 try/finally로 deinit()을 보장하는 코드를 반복해서 작성하고 있다. 라이브러리를 사용하는 예제에 자주 등장하는 with 문은 이 반복을 어떻게 줄여 주는 걸까?

with 문은 시작과 끝이 있는 자원을 안전하게 쓰기 위한 문법이다. 블록을 정상 종료하든 예외로 탈출하든 상관없이 정리 코드가 반드시 실행된다. try/finally가 보장하는 것과 같지만, 정리 로직을 클래스 안에 캡슐화해 호출하는 쪽 코드를 더 간결하게 만든다.

### 컨텍스트 매니저 만들기

클래스에 __enter__()와 __exit__() 두 메서드를 구현하면 with 문에서 쓸 수 있는 컨텍스트 매니저가 된다.

```python
class SafeLed:
    def __init__(self, pin):
        self.pin = pin
        print(f"핀 {self.pin} 초기화")

    def __enter__(self):
        return self           # as 변수에 전달될 인스턴스

    def __exit__(self, exc_type, exc_val, exc_tb):
        print(f"핀 {self.pin} 정리")   # 블록 종료 시 반드시 실행

    def on(self):
        print(f"핀 {self.pin} 켬")

    def off(self):
        print(f"핀 {self.pin} 끔")


with SafeLed(pin=15) as led:
    led.on()
    led.off()
# 블록 종료 → __exit__ 자동 호출 → 핀 15 정리 출력
```

**코드 해설**

with SafeLed(pin=15) as led:는 SafeLed(15) 인스턴스를 만들고 __enter__()를 호출한다. __enter__가 return self로 반환한 인스턴스가 as led에 연결된다. 블록을 나가면 정상이든 예외든 상관없이 __exit__()가 호출된다. exc_type, exc_val, exc_tb는 블록 안에서 예외가 발생했을 때 그 정보가 전달되는 매개변수로, 예외를 따로 처리하지 않을 때는 그냥 두면 된다.

많은 라이브러리가 컨텍스트 매니저를 지원하는 것은 아닌데, 3장부터 이어지는 예제들은 try/finally와 deinit()으로 자원을 정리한다. 다만 필요하다면 이런 클래스를 감싸는 나만의 클래스를 만들어 with 문으로 쓸 수 있는데, 5장의 MLed 클래스가 Matrix를 이 구조로 감싼 예다.

**실행 결과와 확인할 점**

with 블록이 끝나면 직접 정리 메서드를 호출하지 않아도 핀 정리 메시지가 출력되어야 한다. with 블록 안에 raise ValueError()를 추가해 예외를 강제 발생시켜도 __exit__가 먼저 실행되는지 확인한다.

> **알아두기 — try/finally와 with 문의 관계**
> with 문은 try/finally의 더 간결한 표현이다. with obj as x: 블록은 내부적으로 x = obj.__enter__(); try: ... finally: obj.__exit__(...)와 동일하게 동작한다. 예외 처리가 추가로 필요하면 with 블록 안에 try/except를 함께 써도 된다.

> **한 걸음 더**
> SafeLed의 __exit__에서 return True를 추가하고 블록 안에 raise ValueError()를 넣어 본다. True를 반환하면 예외가 억제되어 밖으로 나오지 않는다. 제거하면 ValueError가 전파되는 것과 비교해 본다.

## 가변 타입과 참조

> **풀고 싶은 문제**
> 함수에 색상 리스트를 전달했는데 함수 밖의 원본 리스트가 바뀌어 버렸다. 어디서 실수한 걸까?

### 변경 가능 타입과 변경 불가 타입

파이썬의 타입은 수정 가능 여부에 따라 두 종류로 나뉜다.

변경 가능 타입인 list, dict, bytearray는 내용을 수정해도 메모리 주소가 그대로다. 함수 인자로 전달한 뒤 내부를 수정하면 원본 데이터가 함께 바뀐다.

변경 불가 타입인 int, float, str, tuple은 값을 바꾸면 기존 인스턴스를 수정하는 게 아니라 새 인스턴스를 만들고 변수가 그 새 인스턴스를 가리킨다.

```python
# 변경 가능 타입 예
color = [255, 0, 0]      # 빨강

def dim(c):
    c[0] //= 2           # c는 color와 같은 인스턴스를 가리킴
    c[1] //= 2
    c[2] //= 2

dim(color)
print(color)             # [127, 0, 0] — 원본이 바뀜!

# 독립된 복사본을 만들려면 슬라이싱 또는 list()
color = [255, 0, 0]
dim(color[:])            # color[:]는 새로운 복사본
print(color)             # [255, 0, 0] — 원본 유지
```

**코드 해설**

dim(color)를 호출하면 c는 color와 같은 리스트 인스턴스를 가리킨다. c[0] //= 2는 c가 가리키는 리스트를 수정하므로 color도 바뀐다. color[:]는 모든 원소를 복사한 새 리스트를 만들기 때문에 수정이 color에 영향을 주지 않는다.

**실행 결과와 확인할 점**

첫 번째 dim(color) 호출에서 color가 [127, 0, 0]으로 바뀐 것을 확인한다. color[:]로 전달했을 때는 [255, 0, 0]이 유지되는 것을 비교한다.

> **한 걸음 더**
> 1. (255, 0, 0)처럼 튜플로 색상값을 전달하면 수정 자체가 불가능하다. TiCLE Lite 라이브러의 ws2812 모듈이 색상을 (r, g, b) 튜플로 받는 이유가 여기 있다. 실수로 내부에서 수정해도 원본이 보호된다.
> 2. 딕셔너리도 가변 타입이다. {"r": 255, "g": 0}을 함수에 전달해 내부 값을 바꿔 보고 원본이 변하는지 확인한다.

## 리스트 컴프리헨션

> **풀고 싶은 문제**
> GPIO 핀 5개를 초기화하는 코드를 for 루프로 작성하면 7줄이 된다. 한 줄로 줄일 방법이 있을까?

리스트 컴프리헨션은 기존 데이터에서 새 리스트를 만드는 짧은 표현 방법이다. [표현식 for 변수 in 순서열] 형태로 쓴다. 조건이 있으면 끝에 if 조건을 붙인다.

```python
# for 루프 방식
pins = []
for p in [2, 3, 4, 5, 6]:
    pins.append(p * 2)

# 컴프리헨션 방식: 같은 결과를 한 줄로
pins = [p * 2 for p in [2, 3, 4, 5, 6]]
print(pins)         # [4, 6, 8, 10, 12]

# if 조건: 짝수 핀만 선택
even_pins = [p for p in range(10) if p % 2 == 0]
print(even_pins)    # [0, 2, 4, 6, 8]

# 딕셔너리 컴프리헨션
readings = {"temp": 36.5, "humid": 55.2, "press": 1013.0}
high = {k: v for k, v in readings.items() if v > 100}
print(high)         # {'press': 1013.0}
```

**코드 해설**

if 조건은 for 뒤에 붙여 필터링 역할을 한다. 딕셔너리 컴프리헨션은 {k: v for ...} 형태로 쓰며, readings처럼 딕셔너리의 항목을 조건으로 필터링할 때 유용하다.

**실행 결과와 확인할 점**

even_pins가 [0, 2, 4, 6, 8]로 출력되어야 한다. high에는 1013.0인 press만 들어간다.

> **알아두기 — enumerate로 번호 붙이기**
> for i, (thresh, label) in enumerate(zones):처럼 for 문의 순서열 앞에 enumerate()를 씌우면, 원소마다 (번호, 값) 쌍이 만들어진다. 번호가 필요 없으면 for item in zones:만 쓰면 되지만, 몇 번째 원소인지 함께 써야 할 때는 enumerate가 훨씬 간결하다. zones의 각 원소가 (thresh, label)처럼 튜플이면, for i, (thresh, label) in enumerate(zones):는 번호 i를 꺼낸 뒤 나머지 튜플을 그대로 thresh와 label로 나누어 받는다. 3장의 조도 센서 구간 판별 코드가 이 패턴을 쓴다.

> **한 걸음 더**
> [t * 2 for t in [20, 30, 40] if t > 25]를 실행하고 결과가 무엇인지 먼저 예측해 본다. 예측과 실제 결과를 비교한다.

## 람다 함수

> **풀고 싶은 문제**
> 버튼을 누를 때 실행할 함수를 등록하는 코드를 작성하려 한다. 함수 이름을 따로 정의하지 않고 동작을 바로 전달할 수 있을까?

람다(lambda)는 이름 없는 짧은 함수다. 콜백 등록이나 정렬 기준처럼 함수를 잠깐 전달할 때 쓴다. lambda 인자: 반환식 형태로 작성한다.

```python
# 기존 함수 정의 방식
def double(x):
    return x * 2

# lambda 방식: 같은 동작을 한 줄로
double = lambda x: x * 2
print(double(5))    # 10

# 정렬 기준으로 사용
sensors = [("temp", 36.5), ("humid", 55.2), ("press", 1013.0)]
sorted_sensors = sorted(sensors, key=lambda item: item[1])
print(sorted_sensors)

# 콜백 등록 패턴 (버튼 예)
def register_callback(event, handler):
    print(f"이벤트 {event!r} 에 핸들러 등록됨")
    handler()

register_callback("press", lambda: print("버튼 눌림"))
register_callback("long_press", lambda: print("길게 눌림"))
```

**코드 해설**

lambda item: item[1]은 튜플 item에서 두 번째 값을 꺼내는 함수를 한 줄로 표현한 것이다. register_callback()에 전달한 lambda: print("버튼 눌림")은 인자가 없는 함수를 만든다. 4장의 rgb_led = lambda i, r, g, b: mat.draw_rect(...)처럼, 반복해서 쓰는 짧은 계산에 이름을 붙여 두는 패턴이 하드웨어 제어 코드에서도 자주 등장한다.

**실행 결과와 확인할 점**

sensors가 두 번째 값 기준 오름차순으로 정렬되어 가장 낮은 값 36.5인 temp가 첫 번째에 온다.

> **한 걸음 더**
> sorted(sensors, key=lambda item: item[1], reverse=True)로 바꾸어 내림차순으로 정렬해 본다.

## 함수/메서드 인자 패턴

> **풀고 싶은 문제**
> 라이브러리를 사용하다 보면 Audio(sck=4, ws=5, sd_in=6, sd_out=7)처럼 이름을 붙여 인자를 넘기는 코드를 자주 본다. 이름 없이 순서대로 넘기는 것과 어떻게 다르며, 일부는 왜 반드시 이름을 붙여야만 하는 걸까?

함수나 메서드를 정의할 때 매개변수를 어떻게 선언하느냐에 따라, 호출하는 쪽에서 값을 전달하는 방식이 달라진다. 라이브러리에서 제공하는 다양한 클래스의 생성자 대부분은 인자가 많지만, 자주 쓰는 값은 기본값으로 생략할 수 있고, 중요한 인자는 반드시 이름을 붙여야만 전달할 수 있도록 설계되어 있다. 이 세 가지 선언 방식을 이해하면 라이브러리 문서를 보면서 어떻게 호출해야 하는지 바로 파악할 수 있다.

### 기본 인자값

기본값이 있는 매개변수는 함수를 호출할 때 값을 전달하지 않아도 된다. 자주 쓰는 값을 기본값으로 정해 두고, 특별한 상황에서만 바꾸는 패턴이다. 기본값이 있는 매개변수는 반드시 기본값이 없는 매개변수 뒤에 와야 한다.

```python
def show(i, playing=False):
    label = "▶" if playing else "■"
    print(f"트랙 {i}: {label}")

show(1)                # playing 생략 → False 사용
show(2, True)          # 순서대로 전달
show(3, playing=True)  # 이름으로 전달

def connect(host, port=1883, keepalive=60):
    print(f"접속: {host}:{port}  keepalive={keepalive}")

connect("192.168.1.10")                   # port=1883, keepalive=60 사용
connect("192.168.1.10", 1884)             # port만 바꿈
connect("192.168.1.10", keepalive=30)     # keepalive만 바꿈, port는 기본값
```

**코드 해설**

기본값이 있는 매개변수는 값을 전달하지 않으면 선언된 기본값을 사용한다. connect()처럼 인자가 여럿일 때 중간 인자를 건너뛰고 뒤쪽 인자만 바꾸고 싶다면, keepalive=30처럼 이름을 붙여 전달하면 된다. 이름을 붙이면 순서에 상관없이 원하는 인자만 지정할 수 있다.

**실행 결과와 확인할 점**

connect("192.168.1.10", keepalive=30)을 실행하면 port가 기본값 1883으로, keepalive가 30으로 출력되어야 한다. 기본값이 있는 매개변수를 기본값이 없는 매개변수보다 앞에 쓰면 SyntaxError가 발생한다. def f(a=1, b):를 직접 작성해 확인해 본다.

> **한 걸음 더**
> connect() 함수에 timeout=10을 기본값으로 추가하고, connect("192.168.1.10", timeout=5)처럼 timeout만 바꾸어 호출하는 예제를 작성해 본다.

### 가변 인자

매개변수 이름 앞에 *를 붙이면 개수가 정해지지 않은 인자를 튜플로 한 번에 받는다. **를 붙이면 이름을 가진 키워드 인자를 딕셔너리로 받는다.

```python
def log(*messages):
    for msg in messages:
        print("[LOG]", msg)

log("시작")
log("센서 초기화", "온도:", 36.5)

def configure(**options):
    for key, val in options.items():
        print(f"  {key} = {val}")

configure(brightness=0.5, speed=100, loop=True)

def send(topic, payload, **mqtt_opts):
    print(f"발행: {topic} → {payload}")
    if mqtt_opts:
        print(f"옵션: {mqtt_opts}")

send("ticle/light", "on")
send("ticle/light", "on", qos=1, retain=True)
```

**코드 해설**

*messages는 인자를 개수 제한 없이 튜플로 받는다. **options는 키워드 인자를 딕셔너리로 받는다. send()처럼 일반 매개변수 뒤에 **를 붙인 매개변수를 추가하면, 미리 정해지지 않은 선택 옵션을 유연하게 받을 수 있다.

라이브러리 코드에서는 with 문이 전달하는 예외 정보를 받을 때 def __exit__(self, *args):처럼 쓰는 경우가 있다. 전달받는 인자가 무엇인지 이름으로 구분하지 않아도 될 때 *args로 한 번에 받는 것이다.

**실행 결과와 확인할 점**

send() 두 번째 호출에서 mqtt_opts가 {'qos': 1, 'retain': True}로 출력되어야 한다. *args와 **kwargs를 한 함수에 함께 쓸 때는 * 매개변수가 ** 매개변수보다 앞에 와야 한다. def f(**kw, *args):를 작성해 SyntaxError를 직접 확인한다.

> **알아두기 — 딕셔너리를 \*\*로 풀어서 전달하기**
> 함수를 정의할 때 **options는 여러 키워드 인자를 하나의 딕셔너리로 모으지만, 반대로 호출할 때 딕셔너리 앞에 **를 붙이면 그 딕셔너리를 낱개의 키워드 인자로 풀어서 전달한다. kwargs = {"speed": 80}; kwargs["loop"] = True처럼 딕셔너리를 미리 만들어 두고 나중에 func(**kwargs)로 호출하면, 인자 개수나 이름을 실행 중에 결정할 수 있다. 5장의 getattr(fx, name)(**kwargs)가 이 방식으로 이펙트 함수마다 다른 옵션을 전달한다.

> **한 걸음 더**
> log()를 *messages 없이 리스트 인자 하나로 바꾸어 보고, 호출하는 쪽 코드가 어떻게 달라지는지 비교한다.

### 키워드 전용 인자

매개변수 목록에 * 하나만 단독으로 쓰면, 그 뒤에 오는 매개변수는 반드시 이름을 붙여 전달해야 한다.

```python
def init_i2c(*, sda, scl, freq=400_000):
    print(f"I2C: sda={sda} scl={scl} freq={freq}")

init_i2c(sda=12, scl=13)                # OK
init_i2c(sda=12, scl=13, freq=100_000)  # OK
# init_i2c(12, 13)                      # TypeError: 위치 인자로 전달 불가

def init_audio(*, sck, ws, sd_in, sd_out):
    print(f"I2S: sck={sck} ws={ws} sd_in={sd_in} sd_out={sd_out}")

init_audio(sck=4, ws=5, sd_in=6, sd_out=7)   # OK
# init_audio(4, 5, 6, 7)                     # TypeError: 위치 인자로 전달 불가
```

**코드 해설**

* 뒤에 오는 인자는 이름 없이 순서로는 전달할 수 없다. init_i2c(12, 13)보다 init_i2c(sda=12, scl=13)이 훨씬 읽기 쉽고, 실수로 순서를 바꿔 전달할 위험도 없다. init_audio()처럼 인자가 네 개나 되면 이름 없이 순서만으로 sck, ws, sd_in, sd_out을 구분하기 어려워, 순서를 착각해 전달해도 오류 없이 엉뚱한 핀에 연결될 위험이 있다. 이렇게 핀 번호를 잘못 전달하면 장치가 동작하지 않을 수 있으므로, 라이브러리 설계 차원에서 이름을 강제하는 것이다.

TiCLE Lite 라이브러리의 거의 모든 클래스의 생성자가 이 방식을 쓴다. I2CController(sda=10, scl=11), Audio(sck=4, ws=5, sd_in=6, sd_out=7)처럼 쓰는 이유가 여기 있다.

**실행 결과와 확인할 점**

init_i2c(12, 13)을 실행하면 TypeError가 발생해야 한다. 이름을 붙이면 오류가 사라지는 것을 비교한다. init_audio(4, 5, 6, 7)도 마찬가지로 TypeError가 발생하는지 확인한다.

> **알아두기 — \* 단독과 \*args의 차이**
> *args는 인자를 받아 튜플로 모은다. * 단독으로 쓰면 인자를 받지 않고 구분자 역할만 한다. def f(a, *, b, c):에서 a는 위치로 전달할 수 있고, b와 c는 이름을 붙여야 한다. def f(*args, b, c):로 써도 b와 c가 키워드 전용이 된다.

> **한 걸음 더**
> init_audio() 정의에서 sck에만 기본값 4를 지정하고 나머지는 그대로 키워드 전용으로 남겨 본다. init_audio(ws=5, sd_in=6, sd_out=7)처럼 sck를 생략한 호출이 되는지 확인한다.

## global과 nonlocal

> **풀고 싶은 문제**
> 버튼 콜백 함수 안에서 바깥에 있는 카운트 변수를 1씨 늘리려 했는데 UnboundLocalError가 발생했다. 이 에러는 왜 나고, 어떻게 고치는가?

파이썬은 함수 안에서 변수에 값을 대입하면 그 변수를 함수의 새 지역 변수로 취급한다. 바깥에 있는 같은 이름의 변수를 그대로 수정하고 싶다면, 그 변수가 모듈 최상위에 있는지 아니면 감싸는 함수 안에 있는지에 따라 global 또는 nonlocal을 선언해야 한다.

### global 키워드

IRQ나 Timer에 등록하는 콜백 함수는 보통 모듈 최상위에 def로 정의한다. 이런 함수 안에서 모듈 최상위의 변수를 수정하려면 global을 선언한다.

```python
click_count = 0

def on_press():
    global click_count       # 모듈 최상위의 click_count를 수정하겠다는 선언
    click_count += 1
    print(f"클릭 횟수: {click_count}")

on_press()   # 클릭 횟수: 1
on_press()   # 클릭 횟수: 2
print(click_count)    # 2
```

**코드 해설**

global 없이 click_count += 1을 쓰면, 파이썬은 click_count를 함수 안에서 새로 만드는 지역 변수로 판단한다. += 연산은 먼저 기존 값을 읽어야 하는데, 아직 만들어지지 않은 지역 변수를 읽으려다 UnboundLocalError가 발생한다. global click_count를 선언하면 함수 안의 click_count가 모듈 최상위의 click_count를 그대로 가리키므로 대입한 값이 함수 밖에서도 유지된다. 4장의 메뉴 전환 코드(global main_idx, sub_idx)와 5장의 버튼·타이머 콜백(global pressed, changed, global running 등)이 모두 이 패턴을 쓴다.

**실행 결과와 확인할 점**

on_press()를 두 번 호출하면 클릭 횟수: 1과 클릭 횟수: 2가 차례로 출력되고, 마지막 print(click_count)는 2를 출력해야 한다. global 선언을 지우고 다시 실행해 UnboundLocalError가 발생하는 것을 확인한다.

> **한 걸음 더**
> on_press() 안에 click_count = 0을 따로 조건문으로 추가해 두 번 누를 때마다 카운트를 0으로 되돌리는 reset 기능을 만들어 본다.

### 클로저

클로저(closure)는 함수가 자신을 정의한 바깥 함수의 변수를 기억하고 접근하는 구조다. 바깥 함수가 실행을 마친 뒤에도 안쪽 함수가 그 변수를 살아있는 상태로 유지한다.

```python
def make_counter(start=0):
    count = [start]

    def increment():
        count[0] += 1
        return count[0]

    return increment


counter_a = make_counter()
counter_b = make_counter(10)

print(counter_a())   # 1
print(counter_a())   # 2
print(counter_b())   # 11  — counter_a와 독립적
```

**코드 해설**

make_counter가 반환된 뒤에도 count는 메모리에 살아남는다. increment가 count를 참조하고 있기 때문이다. counter_a와 counter_b는 각각 독립된 count 변수를 갖는다.

### nonlocal 키워드

global은 모듈 최상위 변수에만 쓸 수 있다. make_state()처럼 함수 안에 정의된 함수에서 감싸는 함수의 변수를 직접 수정하려면 nonlocal을 선언해야 한다.

```python
def make_state():
    running = False

    def start():
        nonlocal running        # 바깥의 running을 수정하겠다는 선언
        running = True
        print("시작")

    def stop():
        nonlocal running
        running = False
        print("정지")

    def status():
        print(f"현재 상태: {'실행 중' if running else '정지'}")

    return start, stop, status


start, stop, status = make_state()
start()
status()    # 실행 중
stop()
status()    # 정지
```

**코드 해설**

nonlocal 없이 running = True처럼 쓰면 파이썬은 running을 함수 내부의 새 지역 변수로 만든다. 바깥의 running은 건드리지 않는다. nonlocal running을 선언하면 바깥의 running을 직접 수정한다. 5장의 _thread 예제에서 두 스레드가 함께 쓰는 큐 인덱스를 내부 함수에서 갱신할 때 이 패턴이 등장한다.

**실행 결과와 확인할 점**

start() 호출 후 status()가 "실행 중"을, stop() 후가 "정지"를 출력해야 한다. nonlocal을 제거하면 UnboundLocalError 또는 상태 변경 없음 현상을 직접 확인해 본다.

> **알아두기 — global과 nonlocal의 차이**
> global은 모듈 최상위(전역) 변수를 가리키고, nonlocal은 감싸는 함수(지역 스코프)의 변수를 가리킨다. 모듈에 곧바로 정의한 on_press()같은 함수에서는 nonlocal을 쓸 수 없다 — nonlocal이 가리킬 바깥 함수 스코프가 없기 때문이다. 반대로 make_state()처럼 함수 안에 정의된 함수에서 바깥 함수의 변수를 고치려면 nonlocal을 쓰고, global을 쓰면 엉뚱하게 모듈 최상위 변수를 찾는다.

> **한 걸음 더**
> make_counter를 nonlocal 버전으로 다시 작성해 본다. count = [start] 대신 count = start로 쓰고, nonlocal count로 count += 1이 동작하게 한다.

## bytes와 bytearray

> **풀고 싶은 문제**
> I2C 센서가 데이터를 바이트 단위로 전송한다. 파이썬에서 바이트 데이터를 어떻게 만들고 읽는가?

하드웨어 통신에서는 데이터를 바이트 단위로 주고받는다. bytes는 수정 불가능한 고정 바이트 시퀀스이고, bytearray는 내용을 바꿀 수 있는 가변 바이트 시퀀스다.

```python
# bytes: 고정 버퍼 (수신 완료된 데이터 보관)
packet = bytes([0x02, 0xA4, 0xFF])
print(f"패킷: {packet}")           # b'\x02\xa4\xff'
print(f"첫 바이트: {packet[0]}")   # 2
print(f"길이: {len(packet)}")      # 3

# bytearray: 가변 버퍼 (데이터를 조각씩 조립할 때)
buf = bytearray(4)                  # 4바이트짜리 0으로 채운 버퍼
buf[0] = 0x01
buf[1] = 0x10
print(f"버퍼: {buf}")              # bytearray(b'\x01\x10\x00\x00')

# 조각 수신 후 bytes로 변환
buf2 = bytearray()
buf2.append(0x01)
buf2.extend([0x02, 0x03])
packet2 = bytes(buf2)              # 수정 불가 버전으로 고정
print(f"완성 패킷: {packet2}")

# 2바이트 정수 변환 (빅 엔디안, I2C 센서에서 흔히 쓰임)
raw = bytes([0x09, 0xC4])          # 0x09C4 = 2500
value = (raw[0] << 8) | raw[1]
print(f"측정값: {value}")          # 2500
```

**코드 해설**

bytearray(4)는 0으로 채운 4바이트짜리 버퍼를 만든다. 인덱스로 개별 바이트에 접근하여 수정할 수 있다. I2C 센서는 측정값을 2바이트로 나눠 전송하는 경우가 많다. raw[0] << 8은 상위 바이트를 8비트 왼쪽으로 이동한 뒤 하위 바이트 raw[1]과 OR 연산으로 합쳐 16비트 정수를 복원한다.

**실행 결과와 확인할 점**

(0x09 << 8) | 0xC4 = 0x09C4 = 2500이 출력되어야 한다. bytes는 인덱스로 읽을 수 있지만 수정하려 하면 TypeError가 발생하는 것을 확인한다.

> **알아두기 — int.from_bytes()**
> value = int.from_bytes(raw, "big")처럼 쓰면 비트 연산 없이 같은 결과를 얻는다. MicroPython에서도 동작하며 3바이트 이상의 변환에 편리하다.

> **한 걸음 더**
> bytes([0x00, 0xFF])에서 16비트 정수를 복원하면 얼마가 나오는지 계산하고 코드로 확인한다. int.from_bytes()와 비트 연산 두 방법 모두 써서 같은 결과가 나오는지 비교한다.

## 모듈과 임포트

> **풀고 싶은 문제**
> from ticle_lite.ws2812 import Matrix, Effect처럼 from 방식과 import 방식이 있는데, 차이는 무엇이고 언제 어느 것을 써야 하는가?

### import 방식 vs from import 방식

import 방식은 모듈 전체를 불러오고, 내부 인스턴스를 쓸 때 모듈이름.인스턴스처럼 앞에 이름을 붙인다. from import 방식은 모듈 안의 특정 인스턴스만 현재 공간으로 직접 불러온다. 이름 앞에 모듈 이름을 붙이지 않아도 된다.

```python
import time
from time import sleep_ms           # MicroPython 전용

time.sleep_ms(100)                  # import 방식
sleep_ms(100)                       # from import 방식 — 같은 동작

# ticle_lite 라이브러리 임포트 예
from ticle_lite.ws2812 import Matrix, Effect
from ticle_lite.button import Button
from ticle_lite.ain import Ain
```

**코드 해설**

from ticle_lite.ws2812 import Matrix, Effect는 ws2812 모듈에서 Matrix와 Effect만 가져온다. 이후 코드에서 Matrix(...)처럼 클래스 이름만으로 쓸 수 있다. 한 모듈에서 여러 클래스를 쓸 때 쉼표로 나열하면 된다.

### if __name__ == "__main__" 패턴

파이썬 파일을 직접 실행할 때와 다른 파일이 불러올 때를 구분하는 패턴이다.

```python
# my_sensor.py
def read_distance(trig, echo):
    # 실제 측정 코드
    return 25.0

if __name__ == "__main__":
    # 이 파일을 직접 실행할 때만 아래 코드가 동작
    dist = read_distance(trig=2, echo=3)
    print(f"거리: {dist} cm")
```

**코드 해설**

파일을 직접 실행하면 __name__이 "__main__"이 되어 아래 테스트 코드가 동작한다. 다른 파일에서 import my_sensor처럼 불러오면 __name__이 "my_sensor"가 되어 테스트 코드는 실행되지 않는다. 실습 예제 파일 끝에 자주 등장하는 if __name__ == "__main__": main() 패턴이 여기서 나온 것이다.

**실행 결과와 확인할 점**

파일을 직접 실행하면 측정값이 출력된다. 다른 .py 파일에서 from my_sensor import read_distance만 하면 print가 실행되지 않는 것을 확인한다.

> **한 걸음 더**
> 현재 작성 중인 스크립트에서 print(__name__)을 실행해 본다. 직접 실행할 때와 import할 때 값이 어떻게 다른지 확인한다.

## 정리

이 장에서 다룬 개념은 이후 실습 코드 전반에 반복해서 등장한다.

| 개념 | 핵심 용도 |
|---|---|
| 클래스와 인스턴스 | 하드웨어 라이브러리 인스턴스 생성과 메서드 호출 |
| 예외 처리 | 하드웨어 초기화 실패 대응, 종료 시 자원 정리 |
| with 문과 컨텍스트 매니저 | 장치 인스턴스 자원 정리(deinit) 자동화, 종료 시 정리 보장 |
| 가변 타입과 참조 | 함수에 리스트, 딕셔너리를 전달할 때 원본 보호 |
| 리스트 컴프리헨션 | 핀 목록, 필터링된 센서값 등 간결한 리스트 생성 |
| 람다 함수 | 버튼, 이벤트 콜백을 한 줄로 등록 |
| 함수 인자 패턴 | 기본값으로 생략 허용, 키워드 전용으로 라이브러리 인터페이스 명확화 |
| global과 nonlocal | 콜백에서 전역 변수 수정(global), 스레드 공유 변수와 클로저 상태 유지(nonlocal) |
| bytes와 bytearray | I2C, BLE 통신의 바이트 데이터 처리 |
| 모듈과 임포트 | 라이브러리 불러오기, 실행 진입점 구분 |

2. try/except/finally 구조에서 finally 블록이 항상 실행되는 이유를 설명하고, 하드웨어 코드에서 finally가 필요한 상황을 예를 들어 서술하시오.
3. with 문에서 __enter__와 __exit__가 각각 어떤 시점에 호출되는지 설명하고, try/finally와 어떤 점에서 같고 다른지 서술하시오.
4. 리스트를 함수에 전달했을 때 원본이 수정되는 이유를 변경 가능 타입의 특성으로 설명하고, 원본을 보호하는 방법을 서술하시오.

9. bytes와 bytearray의 차이를 설명하고, 수신 버퍼처럼 내용을 조각씩 추가해야 하는 상황에서는 어느 타입이 적절한지 서술하시오.
